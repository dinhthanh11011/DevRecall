# DevRecall: Build Progress

The single source of truth for what's done and what's next. **Any new session: read this file first**, then [`CLAUDE.md`](CLAUDE.md) and [`docs/CONTENT_GUIDE.md`](docs/CONTENT_GUIDE.md).

## How to continue (from any new window)

**Current phase: lessons** (full theory pages per track, see *Lessons* below). Question banks are all drafted.

1. `npm install && npm run validate && npm run progress`: see the current state below.
2. Pick the next item, in this order:
   - a lesson file with `status: planned` (a stub whose outline is already agreed): write it, in a **mini-batch** (≤ 2 per track per run, see *Lessons › Mini-batches*);
   - otherwise the next track in *Lesson batches* whose state is `todo`: outline it as `planned` stubs, then write them;
   - otherwise an unchecked box in *App features*.
3. Write content following `docs/CONTENT_GUIDE.md` (§9 for lessons), then run `npm run validate -- --track <id>`.
4. Run `npm run progress`, then add one line to the *Work log* (date, what, next).
5. Definition of done: the validator passes with no warnings, `status: drafted`, and `verify: true` on uncertain facts. A human fact-check is what makes it `reviewed`.

### Mini-batches (from 2026-10-06): small, resumable runs

The remaining `planned` lessons (25, 27, 31–36) are written in **mini-batches**, so each run stays small and any new window can pick up where the last one stopped:

- One run = **at most 2 `planned` lessons per track**, one agent per track (≤ 8 agents, ≤ 16 lessons).
- Lean agent rules: reuse what's already run, at most one small runnable snippet per lesson, one Docker container shared across lessons, aim ~2.5–3.5K validator words, validate once per lesson, grep only the needed question ids from the track YAML, report in ≤ 10 lines.
- After a run: `npm run validate` (0/0) → `npm run progress` → Work log line → **commit + push `main`**. Committing `planned` stubs is fine (they're hidden in the app).
- Next run = whatever still says `status: planned` (`grep -l "status: planned" content/lessons/*/*.md`). When none is left, finish with `npm run build` and a Mermaid render check.

Per track: (1) read the track YAML, its `notionRefs` and the Notion map entry in `../.claude/skills/senior-interview/references/notion-map.md`; open the Notion sub-pages read-only as a topic checklist → (2) write the outline as `planned` stubs → (3) write the lessons (one agent per track within a batch) → (4) `npm run validate -- --track <id>` → (5) `npm run progress` + a Work log line. Finish a batch with `npm run build` and a browser render check of the new Mermaid diagrams.

### Notion › SQL Databases subtree (found while writing the 13-sql-postgres lessons)

- **SQL Databases (storage) / Indexes › Clustered Indexes**
  - "The PK is clustered, no separate heap" and "`friends_pkey` is clustered" are true for SQL Server/InnoDB, not Postgres. In Postgres every table is a heap, the PK is a secondary B-tree pointing to `ctid`, and `CLUSTER` reorders once.
  - "Non-clustered indexes point to memory addresses" is wrong: they store TIDs (block, offset) on disk.
  - "The page is overwritten back to disk" on write is wrong. Postgres changes the page in shared buffers, bgwriter/checkpointer writes it later, and durability comes from the WAL fsync at commit.
- **Indexes › Searching / B-Tree Internals**
  - "1M entries ≈ 20 jumps" describes a binary tree. A B-tree fans out hundreds per page, so 3–4 levels.
  - VACUUM doesn't defragment an index; use `REINDEX CONCURRENTLY`.
  - "A lookup ≈ 1–2 ms" only holds for disk reads. Cached lookups take µs.
- **Execution plan**
  - `UPDATE STATISTICS` is SQL Server; Postgres uses `ANALYZE` / `CREATE STATISTICS`.
  - "Read right-to-left" is SQL Server's graphical plan. A Postgres text plan is read from the most-indented node outward.
  - "n! plans / Volcano-Cascades" is wrong. Postgres uses bottom-up DP, GEQO at `geqo_threshold` = 12, and `join_collapse_limit` = 8.
  - "IO = 90% of cost" isn't a Postgres rule.
- **How DB execute a query?**: the rewriter does not do predicate pushdown, subquery unnesting or CTE inlining; those are planner steps. The rewriter only expands views/rules and applies RLS.
- **LIMIT, GROUP BY, HAVING**: `HAVING SUM(amount) > 100` ≠ `WHERE amount > 100`. Only non-aggregate conditions can move to WHERE.
- **Transactions**
  - The xid is assigned at the first write, not at BEGIN; read-only transactions get a virtual xid.
  - "Changes live in a private workspace / ROLLBACK discards them" is wrong. Uncommitted tuples are in the shared heap, hidden by visibility; ROLLBACK just marks the xid aborted in `pg_xact`, and VACUUM cleans up. There's no UNDO phase.
  - "Background processes merge WAL into data files" is wrong. The checkpointer/bgwriter write dirty buffers, and WAL is replayed only in recovery.
- **Transactions › Isolation Levels**
  - "Serializable = many locks, deadlock-prone" is wrong. Postgres SSI uses non-blocking SIRead locks, and its cost is 40001 retries.
  - "RR has phantoms" isn't true in Postgres.
  - "Higher isolation = more locks" doesn't hold under MVCC.
  - "OLTP usually uses RR" is wrong: most use RC.
  - Write skew is missing.
- **ACID**: "a commit is never lost" doesn't hold with `synchronous_commit = off` or fsync-lying storage.
- **Update & Locking Flow**
  - Row locks aren't an in-memory structure and SELECTs don't check them. Postgres keeps row locks in the tuple header (`xmax` + infomask), and plain reads don't wait for them.
  - It isn't an in-place update in memory: Postgres writes a new version (HOT when possible).
  - The note misses that every UPDATE also takes a table-level ROW EXCLUSIVE lock.
- **Database migration**
  - "`ADD COLUMN … DEFAULT 0` rewrites the table" has been wrong since PG 11: non-volatile defaults are instant, and only volatile ones like `gen_random_uuid()` rewrite.
  - "`SET NOT NULL` is safe" is wrong, because it scans under ACCESS EXCLUSIVE. Use `CHECK … NOT VALID` → `VALIDATE` → `SET NOT NULL` (PG 12+).
  - `UPDATE … LIMIT` and `MODIFY` are MySQL; Postgres can't reorder columns.
  - `ADD COLUMN … NOT NULL` without a default fails immediately on a non-empty table rather than locking for minutes.
  - The steps in the "change data type" recipe are scrambled.
- **Database Replication**
  - "Sleep 100 ms before reading the replica" guarantees nothing.
  - A sticky session gives only monotonic reads, not read-your-writes.
  - Postgres has no statement-based replication and no "semi-synchronous" mode; the equivalent is `synchronous_standby_names = 'ANY 1 (…)'`.
- **Consistent Hashing**: Redis Cluster uses 16,384 fixed hash slots, not a ring.
- **Soft delete**
  - `DELETE … LIMIT` is MySQL.
  - `deleted_at` should be `timestamptz`.
  - "GDPR" as a benefit is wrong, because soft delete isn't erasure.
  - The partial unique index is required, not optional, and it belongs on the lookup columns (`lower(email)`), not on `id`.
- **N + 1 Query**
  - JOIN as "the standard fix" ignores JOIN + LIMIT: `LIMIT 50` returned only 10 orders in a test, so paginate the parent first. It also ignores cartesian explosion.
  - A correlated subquery runs per row (SubPlan).
- **Cách paginate dữ liệu lớn?**: the cursor has no unique tie-breaker and no matching index. "Seek method" is keyset itself, not a separate technique.
- **Normalization**: the normalized `order_items` drops `unit_price`, but the price paid is its own fact.
- Empty pages: Sharding Database, Cách ngăn SQL Injection?.

### Notion › networking & JS notes (found while writing the L1 lessons)

- **HTTP / HTTPS - SSL/TLS**: "the attacker needs the server's private key to decrypt traffic" is wrong with (EC)DHE forward secrecy. A leaked key allows impersonation afterwards, but can't decrypt recorded sessions (source: RFC 8446 §1.2).
- **VPN**: "a VPN always encrypts all data, even HTTP" is wrong. It encrypts only the client → VPN-server hop. Traffic after that server is plaintext again, and split tunnels bypass the VPN entirely.
- **Web Socket**: "the LB must be sticky or you get a reconnect loop" is wrong. An upgraded WebSocket is one TCP connection. Stickiness is only needed for Socket.IO/Engine.IO long-polling (source: Socket.IO docs, *Using multiple nodes*).
- **Socket.IO**: `socket.on("reconnect")` has been `socket.io.on("reconnect")` (on the Manager) since v3 (verify).
- **Server-Sent Events**: setting `Connection: keep-alive` is unnecessary on HTTP/1.1 and forbidden on HTTP/2 (source: RFC 9113 §8.2.2).
- **Backend › NodeJS**
  - "`process.nextTick` > `Promise.then`" only holds in CommonJS. In an ESM entry, promise microtasks from top-level code run first. Measured on Node 24.
  - "`Promise.all` runs the promises in parallel" is wrong. Combinators only wait. Work starts when each promise is created, and losers are never cancelled, so use `AbortController`.
  - The `Promise.race` timeout example rejects with a string (no stack), never clears its timer, and doesn't cancel the fetch. Use `AbortSignal.timeout(ms)`.
  - "unhandledRejection is less severe" is wrong. Since Node 15 the default is `--unhandled-rejections=throw`, which crashes the process.
  - CJS vs ESM misses the main difference: CJS exports are value copies, ESM imports are live bindings. It also misses `require(esm)` in recent Node.
